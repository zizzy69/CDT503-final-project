> 面向对象：不了解编程、机器学习或大语言模型的听众  
> 用途：项目 Presentation、课程报告、现场演示准备  
> 依据：当前项目源码、配置和随项目提供的演示资料

## 1. 一分钟项目介绍

本项目实现了一个**本地 PDF 问答系统**。用户导入 PDF 后，系统把文档内容拆成较小片段，建立可搜索的本地资料索引。用户提问时，系统先从资料中找出最相关的片段，再把问题和片段交给本地语言模型组织答案，并展示检索到的文件和页码。与直接向通用聊天机器人提问相比，这种方式能让回答更有文档依据，也方便用户回到原文核对。

系统的核心流程可以概括为：

**PDF 文档 → 提取和切分文字 → 建立语义索引 → 找相关资料 → 本地模型生成回答 → 显示来源**

本项目使用 LangChain 连接处理流程、Chroma 保存本地向量索引、BGE-small 将文字转换为语义向量，并使用 Qwen 在本地生成回答。项目代码没有导入 OpenAI 客户端，也没有调用 OpenAI API。

### 面向听众的开场说法

> “我们做的是一个能查阅本地 PDF 的问答助手。它不是让模型凭记忆回答，而是先在文档里找依据，再根据找到的内容回答，并把相关文件和页码显示出来。”

## 2. 项目要解决什么问题

### 2.1 传统阅读方式的痛点

当资料很多或文档很长时，人工查找需要逐份打开、搜索关键词、对照上下文。普通聊天模型虽然能快速生成文字，但如果没有提供资料，它可能依赖训练时学到的内容回答，产生听起来合理、实际却不符合当前文件的说法。

### 2.2 本项目采用的办法

系统在回答前先检索用户提供的 PDF，把找到的文字片段作为回答依据。若文档没有包含足够信息，提示词要求模型明确表示“根据现有文档无法确定”，而不是补写一个看似确定的答案。

### 2.3 预期价值与边界

| 预期价值 | 不能据此推断的事情 |
|---|---|
| 在一组本地 PDF 中按含义查找内容 | 不能保证每个答案都正确 |
| 回答时显示检索到的来源文件和页码 | 来源显示不等于答案中的每个陈述都已被人工核实 |
| 文档和模型推理在本机运行，不依赖 OpenAI API | 模型文件首次获取仍可能需要网络，除非已准备好本地模型 |
| 可比较不同文本切分大小对结果的影响 | 一次小规模实验不能证明系统适用于所有文档 |

## 3. 用一个图书馆比喻理解系统

可以把系统想成一位图书馆助理：

1. **PDF 是书**：用户提供要查询的资料。
2. **文字切分是做索引卡**：把长文档拆成较短的段落，便于定位。
3. **Embedding 是语义坐标**：把段落和问题转换成一串数字，使意思相近的内容更容易被找到。
4. **Chroma 是索引柜**：保存这些数字和对应原文；它负责查找，不负责写答案。
5. **Retriever 是资料管理员**：根据问题从索引中取回最相关的若干段落。
6. **Qwen 是文字助理**：阅读问题和取回的段落后组织语言生成回答。
7. **来源信息是书目卡片**：告诉用户相关文字来自哪个文件、哪一页。

因此，BGE、Chroma 和 Qwen 的工作并不相同：BGE 将文字转为便于比较的向量；Chroma 保存并搜索向量；Qwen 负责生成自然语言回答。

## 4. 系统架构与一次问答的数据流

### 4.1 架构图

```text
【导入阶段：准备资料索引】
本地 PDF
   │
   ▼
PyPDFLoader：逐页提取可读取的文字和页码
   │
   ▼
RecursiveCharacterTextSplitter：切成有重叠的小片段
   │
   ▼
BGE-small：把每个片段编码成语义向量
   │
   ▼
Chroma：向量与原文片段保存在本机

【问答阶段：检索后生成】
用户问题
   │
   ▼
同一个 BGE-small：把问题编码成向量
   │
   ▼
Chroma：按相似度找出 top-k 个片段（默认 k=4）
   │
   ▼
Prompt：把问题、片段及来源信息组合起来
   │
   ▼
本地 Qwen：根据提供的上下文生成回答
   │
   ▼
网页展示回答、来源片段和页码
```

### 4.2 关键步骤说明

1. **读取 PDF**：`PyPDFLoader` 将 PDF 页面转成文本记录。每条记录保留来源文件和页码，便于后续追踪。
2. **切分文字**：`RecursiveCharacterTextSplitter` 尽量沿段落、换行和标点切分。相邻片段保留一段重叠文字，减少重要内容刚好落在切分边界的风险。
3. **建立语义索引**：BGE-small 为每个片段生成向量，Chroma 将向量、原文和元数据保存在 `vector_store/chroma/`。
4. **检索资料**：用户问题也用同一个 BGE 模型转换为向量，Chroma 按语义相似度返回前 `TOP_K` 个片段。
5. **生成回答**：系统把检索片段和问题写入提示词，交给本地 Qwen。提示词要求模型以资料为依据、尽量标注来源，并在资料不足时说明无法确定。
6. **展示结果**：Gradio 网页显示回答、检索来源和状态信息；来源预览包含片段文字和页码。

## 5. 使用的技术与选择理由

| 技术/组件 | 在项目中的作用 | 面向非技术听众的解释 |
|---|---|---|
| Python | 项目实现语言 | 用来编写系统各步骤的通用语言 |
| LangChain | 连接文档加载、切分、向量库和检索接口 | 流程连接器，避免每个模块都从头对接 |
| PyPDFLoader | 逐页读取 PDF 文本 | 把 PDF 页面内容转成程序可处理的文字 |
| RecursiveCharacterTextSplitter | 按边界切分长文本 | 把一本书拆成便于查找的段落卡片 |
| BGE-small（默认 `BAAI/bge-small-zh-v1.5`） | 将问题和文本编码成向量 | 语义索引器；相似含义的文字通常更容易匹配 |
| Chroma | 在本地保存和检索向量及其对应片段 | 本地资料索引柜 |
| Qwen2.5-Instruct | 阅读检索上下文并生成回答 | 本地运行的文字生成模型 |
| Transformers / PyTorch | 加载模型并执行推理 | 模型运行引擎 |
| Gradio | 提供网页上传和提问界面 | 用户操作的网页窗口 |
| RAGAS | 评估检索上下文和回答相关性 | 用统一指标检查实验结果的评估工具 |

### 5.1 为什么使用 RAG，而不是重新训练模型

本项目没有用自己的课程 PDF 重新训练 Qwen。PDF 内容通过检索在问答时临时提供给模型。这样做的好处是新增或替换资料时可以重新建索引，而不必重新训练大模型；也能让回答与当前资料关联起来。需要注意，RAG 可以降低模型脱离资料回答的风险，但并不能完全消除错误或幻觉。

### 5.2 本地模型与硬件模式

- **检测到 CUDA/GPU 时**：代码选择 `Qwen/Qwen2.5-7B-Instruct`，使用 bitsandbytes 4-bit 量化和自动设备映射。量化用于降低模型占用的显存。
- **没有可用 CUDA 时**：代码选择 `Qwen/Qwen2.5-1.5B-Instruct`，以 CPU 和 float32 运行，不使用 bitsandbytes。
- **Embedding 设备**：默认根据 PyTorch 是否检测到 CUDA 在 GPU 和 CPU 间选择，也可以通过 `EMBEDDING_DEVICE` 指定。
- **模型文件**：模型名称或本地目录通过环境变量配置。项目配置默认优先查找本地缓存；若本地没有模型文件，需要先准备模型，或按需开启下载。

GPU 和 CPU 使用不同规模的生成模型，回答质量、内存占用和速度可能不同。报告应注明实际演示使用的硬件及模型模式，不应把两种模式的结果当作完全相同的条件。

## 7. 重要参数：它们会怎样影响结果

当前源码中的默认值如下。实际运行时可以通过环境变量调整。

| 参数 | 当前默认值 | 含义与影响 |
|---|---:|---|
| `CHUNK_SIZE` | 800 | 每个片段的目标字符数；越小片段越细，越大单段上下文越完整 |
| `CHUNK_OVERLAP` | 120 | 相邻片段共享的字符数；用于降低边界切断信息的影响 |
| `TOP_K` | 4 | 每个问题取回的片段数量；太少可能漏掉依据，太多可能带入无关内容 |
| `TEMPERATURE` | 0.2 | 控制生成随机性；较低通常更适合事实型问答，但不等于保证事实正确 |
| `MAX_NEW_TOKENS` | 512 | 回答最多生成的新 token 数量上限 |
| `COLLECTION_NAME` | 根据 chunk 参数生成 | 指定 Chroma 中使用的集合；不同实验配置应分开保存 |

**长度单位提醒：** 当前切分器使用 Python 字符数计数，不是模型 token 数。中文和英文在 token 化后的长度可能不同。

**实验配置提醒：** 问答模块默认使用 `CHUNK_SIZE=800`、`CHUNK_OVERLAP=120` 建库/打开集合；评估脚本则固定比较 `chunk_size=512` 和 `1024`，并读取 `CHUNK_OVERLAP`（默认 120）。要运行评估，必须先分别建立这两个 collection，并保持 overlap、embedding 模型和数据集一致。

## 8. 评估设计与结果应如何解释

### 8.1 当前评估脚本做什么

`src/evaluation/evaluate.py` 会对测试集里的每个问题，分别运行 512 和 1024 两种切分配置，执行检索和回答，再通过本地 Qwen 作为评估模型计算两项 RAGAS 指标。脚本会生成：

- `evaluation_results/ragas_chunk_comparison.csv`：每组实验的平均分和题目数量。
- `evaluation_results/ragas_chunk_comparison_details.csv`：每道题的参考答案、模型回答、来源、检索上下文及指标。
- `evaluation_results/ragas_chunk_comparison.png`：两组配置的指标柱状图。

可以通过 `EVAL_OUTPUT_DIR` 更改输出目录。

### 8.2 指标是什么

| 指标 | 它主要回答的问题 | 它不能单独证明什么 |
|---|---|---|
| `context_recall`（上下文召回） | 检索到的片段是否覆盖参考答案需要的信息？ | 不直接证明最终回答准确，也不保证所有相关片段都被找全 |
| `answer_relevancy`（回答相关性） | 生成的回答是否围绕用户问题？ | 不直接判断答案中的事实是否正确 |

两项指标都要结合明细和人工检查。特别是 `answer_relevancy` 高，不代表回答内容必然真实。

### 8.3 目前能确认与不能确认的结果

- **可以确认**：源码已实现两个 chunk_size 的评估流程，以及摘要、明细和图表的保存代码。
- **不能仅凭源码确认**：实验是否已成功跑完、具体分数是多少、哪种切分一定更好、系统准确率是多少。
- 本次文档编写没有运行完整模型推理或评估实验，因此没有填写性能数字。

报告结果表建议使用真实运行结果填写：

| 配置 | overlap | 问题数 | 平均 context_recall | 平均 answer_relevancy | 观察/失败案例 |
|---|---:|---:|---:|---:|---|
| chunk_size=512 | 120 | 待运行后填写 | 待运行后填写 | 待运行后填写 | 待人工分析 |
| chunk_size=1024 | 120 | 待运行后填写 | 待运行后填写 | 待运行后填写 | 待人工分析 |

比较时尽量只改变 `chunk_size`，固定 PDF、测试集、overlap、top-k、模型和硬件条件。若改变了其他条件，应在报告中写明。

## 9. Windows PowerShell 运行与实验步骤

以下命令假设终端当前目录为项目根目录 `E:\rag_project`，且已安装兼容的 Python 依赖。GPU 环境的 PyTorch/CUDA 安装要与本机驱动匹配；不要仅凭 `requirements.txt` 推断当前机器已成功启用 CUDA。

### 9.1 准备环境

```powershell
.\venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

首次加载模型前，确认本地模型缓存或 `EMBEDDING_MODEL_NAME`、`LLM_MODEL_NAME` 指向的模型目录已经准备好。若模型尚未缓存，按项目配置获取模型，或确认允许联网下载。

### 9.2 用演示 PDF 建立两个实验集合

演示 PDF 同时存在于 `data/demo_pdfs/` 和 `data/raw/`。导入脚本会递归扫描 `DATA_DIR` 下的 PDF；为避免把两个目录中的同一套演示 PDF 重复纳入实验，建议把本次数据目录明确限定为 `data/raw`：

```powershell
$env:DATA_DIR = (Join-Path $PWD 'data\raw')
$env:CHUNK_OVERLAP = '120'
$env:CHUNK_SIZE = '512'
python -m src.ingestion.ingest

$env:CHUNK_SIZE = '1024'
python -m src.ingestion.ingest
```

两个集合应分别保存为 `pdf_rag_bge_small_cs512_co120` 和 `pdf_rag_bge_small_cs1024_co120`。如需使用其他 overlap，建库和评估阶段都必须设置为相同值。

### 9.3 运行网页演示

```powershell
python -m src.ui.app
```

默认地址绑定 `127.0.0.1:7860`，并尝试在本机浏览器打开。网页选择 PDF 后会自动触发导入；输入问题后可查看回答和检索来源。第一次提问需要加载 embedding 和 Qwen，可能比后续问题慢。默认 `share=False`，不会创建 Gradio 公网分享链接。

### 9.4 运行评估

演示问题在 `data/demo_pdfs/demo_qa_set.json`，而评估脚本默认查找 `data/test_qa_set.json` 或根目录的 `test_qa_set.json`。为了让测试问题与演示 PDF 匹配，明确指定测试集：

```powershell
$env:TEST_SET_PATH = (Join-Path $PWD 'data\demo_pdfs\demo_qa_set.json')
$env:CHUNK_OVERLAP = '120'
python -m src.evaluation.evaluate
```

评估脚本会比较 512 和 1024 两组集合。运行前确认两组集合都已建好；否则会提示相应 Chroma collection 为空。评估也会执行本地 Qwen 推理，耗时取决于模型、设备和问题数量。

### 9.5 参数如何通过 PowerShell 设置

源码以环境变量读取实验参数，并没有为 ingest 脚本实现 `--chunk-size` 这类命令行选项。请在 PowerShell 中设置 `$env:CHUNK_SIZE`、`$env:CHUNK_OVERLAP` 后运行模块命令。两组实验之间修改环境变量即可，不需要改源码。

## 11. 推荐的项目报告结构

### 11.1 摘要

用一段话交代问题、方法、实现、测试对象和实际结果。结果数字必须来自本次运行的 CSV；若尚未完成评估，应明确写“评估尚未完成”，不要填估计值。

### 11.2 问题定义与目标

- 输入：一组本地 PDF 和自然语言问题。
- 输出：基于检索片段生成的回答，并提供来源文件/页码。
- 目标：验证本地检索增强问答流程能否运行，并比较不同文本切分参数。
- 范围边界：本项目原型聚焦 PDF 文本问答，不是通用搜索引擎，也不承诺零幻觉。

### 11.3 方法与系统架构

## 12. 演示脚本与建议问题

### 12.1 现场演示顺序

5. 展示回答以及对应来源、页码，说明观众可以回到原文核对。

## 13. 局限、风险与改进方向

1. **PDF 文本提取**：当前流程使用文本解析器；若 PDF 是扫描图片或文字层质量差，系统可能提取不到正确文字。未来可评估 OCR。
2. **模型可能答错**：检索到的内容不充分、模型误读上下文或生成时补充了无依据内容，都可能导致错误。重要结论仍需人工核对原文。
3. **来源不是逐句事实校验**：界面显示的是检索到的来源片段，并不代表模型回答中每句话都已自动验证。
4. **语言与资料匹配**：默认 embedding 是中文 BGE-small；项目演示资料和现有测试问题包含英文。跨语言或英文语料的检索表现需要实际测量，不能仅凭模型名称作结论。
5. **硬件影响体验**：GPU 4-bit 7B 和 CPU 1.5B 的速度、内存占用及输出质量可能不同。报告应记录实际设备和模型模式。
6. **测试规模有限**：少量合成演示 PDF 适合检查流程，不足以代表真实课程材料或大型知识库上的表现。
7. **数据目录会递归扫描**：ingest 会查找 `DATA_DIR` 下所有 PDF。若同一文件同时存在于 `data/demo_pdfs/` 和 `data/raw/`，两个路径会被当成不同来源处理。正式实验应将 `DATA_DIR` 指向只包含本次实验语料的目录。
8. **模型下载与本地运行的区别**：问答推理可以在本地完成，但首次获取模型权重仍可能需要下载。报告隐私声明应准确描述数据处理和模型获取方式。

### 面对“系统会不会产生幻觉？”的回答

> “有可能。RAG 的作用是先提供文档依据、降低模型凭空回答的机会，但它不是事实正确性的保证。我们通过显示来源、设置资料不足时拒答的提示，并检查测试明细来降低和发现这类风险。”

## 14. 答辩常见问题与建议回答

**问：为什么不直接用 ChatGPT？**  
答：项目约束要求不调用 OpenAI API；同时，本项目希望验证本地资料检索和本地模型推理的完整流程。模型由本地 Transformers 加载，资料索引由本地 Chroma 保存。

**问：BGE 和 Qwen 有什么区别？**  
答：BGE 负责把问题和文档变成便于比较的语义向量，帮助找资料；Qwen 负责阅读找到的资料并组织自然语言回答。

**问：Chroma 是不是大语言模型？**  
答：不是。Chroma 是保存和搜索向量及其对应文字的数据库，不负责生成答案。

**问：RAG 能保证回答正确吗？**  
答：不能保证。它让回答有机会参考检索内容并提供来源，但检索可能漏掉资料，生成模型也可能误解或补充内容，因此要检查来源并用测试集评估。

**问：为什么比较 512 和 1024？**  
答：这是两种文本片段长度。较短片段可能更聚焦，较长片段可能保留更多上下文。哪种适合本项目，需要在相同资料、测试问题和其他参数下运行实验后判断。

**问：项目已经证明哪种方案更好吗？**  
答：只有在两组评估都成功运行并得到可复查的 CSV 后才能回答。应报告实际指标和失败案例，不应把代码中预设的实验设计说成已经验证的结论。

**问：GPU 不可用时系统还能运行吗？**  
答：源码包含 CPU 分支，会切换到 Qwen2.5-1.5B；但模型文件和依赖仍需正确准备，CPU 推理通常会更慢。应以现场实际运行结果为准。

## 16. 可直接用于结尾的总结

> “本项目把本地 PDF 处理、语义检索和本地语言模型生成整合成一个可交互原型。它的重点不只是生成答案，而是先寻找相关资料、展示来源，并通过匹配的测试问题和参数对比来检查效果。当前系统仍受 PDF 文本质量、模型能力、硬件和测试规模限制，因此我们会结合实际实验分数、失败案例和人工核对来评价它，而不把模型输出当作绝对正确的事实。”
